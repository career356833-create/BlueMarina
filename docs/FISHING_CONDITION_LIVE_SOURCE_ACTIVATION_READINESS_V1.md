Both adapters import `server-only` and fail closed unless the flag is exactly `true` and the corresponding key exists. The Vercel project environment inventory contains **none** of these flags, keys, or URL overrides in Preview or Production. The flags therefore take the disabled path. A local `.env.local` key worked for bounded read-only checks; that does not establish a Preview or Production credential. Only names/scopes were inventoried; no key value was recorded. The key is sent in a server-side query URL, not to the browser. Code inspection found no client key reference or key logging, and the Production error responses contained no key. An upstream/network logging service could still record query URLs; inspect such logging before activation.

NIFS's [OpenAPI specification](https://www.nifs.go.kr/openApi/actionOpenapiInfoList.do?contentsCd=01) requires a key and describes RISA's 30-minute generation and FEMO's 2–3-month update cycle. It does not establish a quota, rate limit, or price for this key. All three remain **UNKNOWN**; a successful small request is not quota approval.

## Bounded live evidence

Three initial upstream calls used local keys without printing them. RISA station metadata returned HTTP 200, JSON, code `00`, 41 rows in about 169 ms. Its observation endpoint returned HTTP 200, JSON, code `00`, 65 rows from 41 stations in about 107 ms. Latest source clock was `2026-09-26 12:30:00`, approximately 18 minutes before review, so RISA is *near real time* in this sample. The normalizer joins exact station IDs, selects the latest timestamp per station, retains surface/middle/bottom temperatures in °C, coordinates, missing values, and maintenance flags. The [official API table](https://www.nifs.go.kr/openApi/actionOpenapiInfoList.do?contentsCd=01) does not state the timestamp timezone; `TIMEZONE_NOT_DOCUMENTED` remains correct. Code compares the source wall clock with an Asia/Seoul operational clock for freshness, but this must not be presented as a confirmed source timezone.

FEMO returned HTTP 200, JSON, code `00`, 251 rows and 249 composite fishery/station sites in about 190 ms. A second read-only call checked chronological parsing: samples span `2025-09-26 08:55` through `2025-11-05 10:10`. The newest is about **325 days old** on the review date, far beyond the stated 2–3-month update cadence. All 251 rows contained the surface/bottom temperature, salinity, and DO fields; field presence alone does not prove valid numeric measurement or current relevance. The normalizer preserves source timestamp, coordinates, surface/bottom layers and nulls. The NIFS [observation portal](https://nifs.go.kr/portal/me/femoA/actionDataObsSearch.do) labels temperature °C and DO mg/L. Salinity lacks a documented unit in the inspected API/portal material, so the adapter's `UNIT_NOT_DOCUMENTED` must stay; do not numerically compare it. DO mg/L may be displayed with that official portal label. FEMO source timestamp timezone is also undocumented. Existing code marks FEMO fresh through 120 days and stale through 365 days; a 325-day sample is stale, and the 365-day boundary should be reviewed against source cadence before activation.

These are bounded point-in-time checks, not evidence of sustained upstream stability. No arbitrary quota or cost was inferred.

## Behavior and failure isolation

Production currently returns `503 SOURCE_DISABLED` from both observation-only APIs. A profile-only read-model POST returns HTTP 200 `PARTIAL`, keeps the 38-species `profileContext`, and reports each source `UNAVAILABLE/SOURCE_DISABLED`. For an explicitly selected source, disabled, missing-key, timeout, or generic upstream failure is caught by the read-model route and recovers to HTTP 200 `PARTIAL` with static profile evidence and a limitation. Invalid location and contract failure remain errors rather than invented observations. The sources are selected one at a time; there is no combined RISA+FEMO response that preserves one live source while the other fails. Thus isolation is verified for *static profile versus selected source*, not simultaneously merged live sources.

Fishing Spot coordinates are not observation-station coordinates. The client requires an explicit source, site/station, and depth before live submit; no nearest-station inference runs. A page visit and a profile-only query cause zero NIFS upstream calls. Selecting RISA triggers two cold upstream calls; FEMO triggers one. Submitting a live read-model request can repeat those counts on a different or cold serverless instance. Changing species or station without submit causes no upstream call; submitting on a warm instance normally reuses module cache until TTL. There is no in-flight request coalescing or retry; parallel cold requests and multiple instances can amplify traffic. Server-side timeouts are bounded at 10 s per RISA endpoint (parallel) and 30 s for FEMO. The observation routes also expose CDN caching, while read-model POST uses module cache and `no-store` response headers.

The current static source-status contract uses `UNAVAILABLE` or `NOT_REQUESTED` plus a reason, rather than separate `DISABLED/ERROR/STALE` enums. Observed source freshness is carried in observation/read-model fields. The UI names the source and selected station, shows timestamp, depth and measurements, and retains limitations. Salinity may be shown only as an explicitly unit-unconfirmed raw fact. No new score, rank, probability, recommendation, or automatic suitability verdict was added here. **Activation policy gap:** the older 10-species live path already calls `compareFishingCondition` after explicit submit, including temperature range relations. The newer profile-only path keeps observed values separate. A blanket claim that activation produces no automatic numeric comparison would be false until the older path is adjusted or explicitly gated.

## Preview plan and Production gate

1. Keep Preview and Production disabled now. Acquire server-scoped Preview credentials and confirm the applicable NIFS key scope, quota, and cost terms. Do not put keys in `NEXT_PUBLIC_*`.
2. Resolve the legacy comparison-policy gap for activation, validate FEMO sample freshness and salinity/DO display, and confirm whether the default versus `/api/` FEMO endpoint should be configured.
3. Consider **RISA first** because its current temperature sample and unit are clear. After the preceding gates, enable only RISA in Preview. Verify the 38-species selector, explicit station/depth selection, observation endpoint, read-model, evidence-bundle, timestamps, limitations, source status, browser errors and no client key exposure.
4. Simulate disabled, missing-key, timeout and malformed upstream responses; require static `profileContext` to stay available and the page to avoid a crash. Check concurrent cold-call amplification against a confirmed NIFS quota.
5. Review FEMO separately. A current 325-day-old sample is not a recent observation merely because HTTP is 200. Do not activate until cadence/freshness and unit presentation are accepted in Preview.
6. Only after Preview passes may a separate Production activation decision be made. This review does **not** authorize Production ON.
